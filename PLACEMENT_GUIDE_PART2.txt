7. COMMON INTERVIEW QUESTIONS & ANSWERS
================================================================================

Q1: "Walk me through your project architecture."

ANSWER:
"CloudPulse follows a microservices architecture with three main layers:

1. FRONTEND LAYER: React SPA served by Nginx
   - Handles user interface and interactions
   - Manages client-side state and routing
   - Stores user profiles in localStorage

2. BACKEND LAYER: Node.js/Express API
   - RESTful API with 5 main endpoints
   - Integrates with AWS SDK v3
   - Handles authentication via headers
   - Processes and aggregates data from multiple regions

3. AWS SERVICES LAYER:
   - EC2 for instance data
   - CloudWatch for metrics
   - Cost Explorer for billing

The frontend and backend run in separate Docker containers, orchestrated by 
Docker Compose. They communicate via REST API, and the backend makes parallel 
calls to AWS services across all regions for optimal performance."

Q3: "How do you handle security in your application?"

ANSWER:

1. CREDENTIAL SECURITY:

   - Transmitted via HTTPS headers only
   - User controls credential lifecycle
   - Can be deleted anytime from browser

2. AWS IAM:
   - Least privilege principle
   - Only 4 permissions granted
   - No admin or write access except StopInstances

3. API SECURITY:
   - CORS configured for specific origins
   - Input validation on all endpoints
   - Error messages sanitized

4. CONTAINER SECURITY:
   - Non-root users
   - Minimal Alpine images
   - Regular vulnerability scanning with Trivy

5. CI/CD SECURITY:
   - Automated security scans on every commit
   - CodeQL for SAST
   - Secret detection with TruffleHog
   - Dependency auditing

I also implemented a complete security scanning pipeline that runs daily and 
on every PR."

Q5: "What challenges did you face and how did you solve them?"

ANSWER:
"Three major challenges:

CHALLENGE 1: MULTI-REGION API CALLS TAKING TOO LONG
Problem: Sequential calls to 28 regions took 280+ seconds
Solution: 
- Implemented Promise.all() for parallel execution
- Added per-region error handling
- Reduced time to ~10 seconds
- Added timeout handling (30s per region)

CHALLENGE 2: IDLE INSTANCE DETECTION ACCURACY
Problem: CloudWatch metrics sometimes missing or incomplete
Solution:
- Implemented fallback logic for missing data
- Used 7-day average instead of single point
- Added data validation before calculation
- Graceful degradation if metrics unavailable

CHALLENGE 3: MANAGING MULTIPLE AWS ACCOUNTS
Problem: Users needed to logout/login to switch accounts
Solution:
- Built profile management system
- Stored multiple profiles in localStorage
- One-click account switching
- Added username for better UX

CHALLENGE 4: DOCKER IMAGE SIZE
Problem: Initial images were 1GB+ each
Solution:
- Multi-stage builds
- Alpine base images
- Removed dev dependencies from production
- Final sizes: Frontend 50MB, Backend 200MB"

Q8: "How do you handle errors in your application?"

ANSWER:
"Error handling at multiple levels:

1. FRONTEND:
   - Try-catch blocks for async operations
   - Error boundaries for React components
   - User-friendly error messages
   - Retry mechanisms for failed requests
   - Loading states during operations

2. BACKEND:
   - Express error middleware
   - Per-region error handling (multi-region calls)
   - Graceful degradation
   - Detailed error logging
   - HTTP status codes (400, 401, 500)

3. AWS API:
   - Retry logic with exponential backoff
   - Timeout handling
   - Credential validation
   - Region-specific error handling

Example:
```javascript
try {
  const response = await axios.get('/api/instances');
  setInstances(response.data);
} catch (error) {
  if (error.response?.status === 401) {
    setError('Invalid AWS credentials');
  } else if (error.response?.status === 500) {
    setError('Server error. Please try again.');
  } else {
    setError('Network error. Check your connection.');
  }
}
```"

Q: "How does authentication work?"

ANSWER:
"Authentication flow:

1. USER LOGIN:
   - User enters AWS credentials in UI
   - Stored in browser localStorage
   - Never sent to backend for storage

2. API REQUEST:
   - Frontend includes credentials in HTTP headers:
     * X-AWS-Access-Key-Id
     * X-AWS-Secret-Access-Key
     * X-AWS-Region

3. BACKEND VALIDATION:
   - Extracts credentials from headers
   - Creates AWS SDK client with credentials
   - Makes AWS API call
   - If credentials invalid, AWS returns error
   - Backend forwards error to frontend

4. SESSION MANAGEMENT:
   - No server-side sessions
   - Stateless authentication
   - User can logout (clears localStorage)

Security considerations:
- HTTPS in production (encrypted in transit)
- No credential storage on server
- User controls credential lifecycle
- Credentials validated by AWS directly

Alternative considered:
- JWT tokens: Not needed (stateless design)
- OAuth: Overkill for this use case
- AWS Cognito: Future enhancement"

Q: "Explain your API design."

ANSWER:
"RESTful API design following best practices:

ENDPOINTS:

1. GET /api/health
   - Purpose: Health check
   - Response: { status: 'ok' }
   - Use: Load balancer health checks

2. GET /api/instances
   - Purpose: Fetch all EC2 instances
   - Headers: AWS credentials
   - Response: { instances: [...] }
   - Logic: Parallel calls to all regions

3. GET /api/metrics/:instanceId?region=us-east-1
   - Purpose: Get CloudWatch metrics
   - Params: instanceId (path), region (query)
   - Response: { averageCpu, isIdle, datapoints }
   - Logic: 7-day CPU average calculation

4. POST /api/instances/:instanceId/stop
   - Purpose: Stop EC2 instance
   - Body: { region }
   - Response: { message, stoppingInstances }
   - Logic: AWS StopInstances API call

5. GET /api/billing
   - Purpose: Get cost data
   - Response: { currentMonth, lastMonth, yearToDate, monthlyBreakdown }
   - Logic: Cost Explorer API aggregation

DESIGN PRINCIPLES:
- RESTful conventions
- Proper HTTP methods (GET, POST)
- Meaningful status codes (200, 400, 401, 500)
- JSON responses
- Error handling middleware
- CORS configuration
- Request validation

API Response Format:
Success: { data: {...} }
Error: { error: 'message', details: '...' }"

Q: "How do you handle concurrent requests?"

ANSWER:
"Node.js handles concurrency naturally through its event loop:

1. EVENT LOOP:
   - Non-blocking I/O
   - Single-threaded but asynchronous
   - Can handle thousands of concurrent connections

2. ASYNC/AWAIT:
   - All AWS API calls are async
   - Doesn't block other requests
   - Efficient resource utilization

3. PROMISE.ALL:
   - Parallel execution of region calls
   - All regions queried simultaneously
   - Results aggregated when all complete

4. ERROR ISOLATION:
   - Try-catch per region
   - One failure doesn't affect others
   - Graceful degradation

Example:
```javascript
// Multiple users can call this simultaneously
app.get('/api/instances', async (req, res) => {
  // Each request gets its own execution context
  const instances = await fetchFromAllRegions();
  res.json({ instances });
});
```

For high load:
- Add load balancer
- Run multiple backend instances
- Implement rate limiting
- Add Redis for caching
- Use connection pooling"
